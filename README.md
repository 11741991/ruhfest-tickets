# RUHFEST · Электронные билеты

Минимальная система электронных билетов для трёхдневного фестиваля.

**Сценарий:** менеджер вручную проверил оплату → создал билет → отправил ссылку в WhatsApp → на входе сотрудник сканирует QR → на выходе сканирует ещё раз.

Стек: React + Vite + JavaScript + Supabase + Vercel. Без сервера, без Docker, без платных сервисов.

## Шаг 1. Создать проект Supabase

1. Откройте <https://supabase.com> → **Start your project** → войдите через GitHub.
2. **New project**.
3. Заполните:
   - **Name:** `ruhfest`
   - **Database Password:** придумайте надёжный пароль и сохраните его.
   - **Region:** ближайший регион (например, `Central EU (Frankfurt)`).
4. Нажмите **Create new project** и подождите 1–2 минуты.

## Шаг 2. Выполнить SQL

В левом меню Supabase откройте **SQL Editor** → **New query**.

Выполните три файла **строго по порядку**, каждый в отдельном запросе:

1. Скопируйте всё содержимое `sql/01_schema.sql` → вставьте → **Run**.
2. Новый запрос → содержимое `sql/02_functions.sql` → **Run**.
3. Новый запрос → содержимое `sql/03_rls.sql` → **Run**.

Проверка: **Table Editor** → должны появиться таблицы `tickets` и `scan_logs` с иконкой замка (RLS включён).

## Шаг 3. Создать первого сотрудника

Регистрации на сайте нет — аккаунты создаёт только организатор.

1. Supabase → **Authentication** → **Users** → **Add user** → **Create new user**.
2. Введите email и пароль сотрудника.
3. Включите галочку **Auto Confirm User** (иначе вход не сработает без подтверждения почты).
4. **Create user**.

Повторите для каждого сотрудника на входе и выходе. Отдельных ролей в системе нет: любой авторизованный сотрудник может и создавать билеты, и сканировать.

> Совет: отключите публичную регистрацию — **Authentication → Sign In / Providers → Email → Allow new users to sign up: Off**.

## Шаг 4. Взять URL и anon key

Supabase → **Project Settings** → **API**:

- **Project URL** → это `VITE_SUPABASE_URL`
- **anon / public key** → это `VITE_SUPABASE_ANON_KEY`

⚠️ **`service_role` key копировать нельзя.** Он даёт полный доступ к базе в обход RLS. Во фронтенде используется только `anon` key — это безопасно, потому что доступ ограничен политиками RLS.

## Шаг 5. Запустить локально

Нужен Node.js 18+ (<https://nodejs.org>).

```bash
cd ruhfest-tickets
cp .env.example .env
```

Откройте `.env` и вставьте свои значения:

```
VITE_SUPABASE_URL=https://abcdefghijklm.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
```

Затем:

```bash
npm install
npm run dev
```

Откройте <http://localhost:5173/login>.

> После изменения `.env` перезапустите `npm run dev` — Vite читает переменные только при старте.

## Шаг 7. Разместить на Vercel

1. <https://vercel.com> → войдите через GitHub.
2. **Add New → Project** → выберите репозиторий `ruhfest-tickets` → **Import**.
3. Vercel сам определит Vite. Framework Preset: **Vite**, Build Command: `npm run build`, Output Directory: `dist`.
4. Раскройте **Environment Variables** и добавьте две переменные:
   - `VITE_SUPABASE_URL` = ваш Project URL
   - `VITE_SUPABASE_ANON_KEY` = ваш anon key
5. **Deploy**.

Через минуту получите адрес вида `https://ruhfest-tickets.vercel.app`. HTTPS включён автоматически — камера в браузере будет работать.

Файл `vercel.json` уже содержит rewrite на `index.html`, поэтому прямые ссылки вида `/ticket/xxxx` открываются корректно.

> Если добавили переменные окружения после деплоя — зайдите в **Deployments** и нажмите **Redeploy**.

## Шаг 8. Проверить камеру

1. Откройте `https://ваш-домен.vercel.app/login` на телефоне и войдите.
2. Перейдите на **ВХОД**.
3. Браузер спросит доступ к камере — нажмите «Разрешить».
4. Должна включиться задняя камера.

Если камера не запускается:

- проверьте, что адрес начинается с `https://` (на `http://` камера работает только на `localhost`);
- iPhone: Настройки → Safari → Камера → «Спросить» или «Разрешить», затем обновите страницу;
- Android Chrome: замок в адресной строке → Разрешения → Камера → Разрешить;
- закройте другие вкладки и приложения, использующие камеру, и нажмите «Включить камеру»;
- если картинка чёрная — нажмите «Сменить камеру» или выберите камеру в списке вручную.

### Почему на iPhone бывает чёрный экран

У iPhone несколько задних модулей: `Back Camera`, `Back Dual Wide Camera`, `Back Ultra Wide Camera`, `Back Telephoto Camera`. Все они видны в `enumerateDevices()`, но Safari отдаёт видео не со всех — трек создаётся и считается активным, а кадров нет. Отсюда чёрный прямоугольник с рамкой сканера.

Что сделано в `src/lib/camera.js`:

- constraints `facingMode: { ideal: 'environment' }` вместо `{ exact: 'environment' }` — `exact` на iOS даёт `OverconstrainedError` либо как раз чёрный поток;
- предыдущий `MediaStream` всегда останавливается (`track.stop()`) и отвязывается от `<video>` до открытия нового — иначе камера остаётся занятой и следующий запрос возвращает пустой кадр;
- поток привязывается к собственному `<video>` с `playsinline`, `webkit-playsinline`, `autoplay`, `muted` — выставленными и атрибутом, и свойством (иначе iOS открывает полноэкранный плеер или блокирует автозапуск);
- `video.play()` вызывается строго после события `loadedmetadata`, с таймаутом на случай зависшего потока;
- после запуска кадр проверяется на яркость: если камера отдаёт только чёрное, задние модули автоматически перебираются по `deviceId` в порядке «основная → вспомогательные»;
- при возврате на вкладку (`visibilitychange`, `pageshow`) поток пробуждается через `play()`, а при `track.ended` предлагается перезапуск.

Распознавание QR выполняется своим циклом: кадр `<video>` → `canvas` → `jsQR`, примерно 10 раз в секунду, кадр уменьшается до 640 px по длинной стороне. Библиотека, которая сама открывает камеру, здесь не используется — иначе описанные выше constraints задать невозможно.

## Шаг 9. Тест двойного сканирования

Полный сценарий проверки:

1. `/admin` → **Создать билет** → имя `Тест`, телефон `+7 700 000 00 00` → **Создать билет**.
2. Нажмите **Копировать ссылку** и откройте её на втором телефоне (или в другом браузере) — увидите QR-код.
3. На первом телефоне: **ВХОД** → отсканируйте QR.
   → Зелёный экран **ВХОД РАЗРЕШЁН**, имя, номер, время. Статус в `/admin` стал **Внутри**.
4. Нажмите **Сканировать следующий билет** и отсканируйте **тот же** QR ещё раз.
   → Красный экран **БИЛЕТ УЖЕ НАХОДИТСЯ НА ТЕРРИТОРИИ**. Статус не изменился.
5. Перейдите на **ВЫХОД** → отсканируйте.
   → Синий экран **ВЫХОД ЗАРЕГИСТРИРОВАН**. Статус стал **Снаружи**.
6. Отсканируйте на **ВЫХОДЕ** ещё раз.
   → Красный экран **ПО ЭТОМУ БИЛЕТУ ВХОД НЕ БЫЛ ЗАРЕГИСТРИРОВАН**.
7. Вернитесь на **ВХОД** и отсканируйте — снова **ВХОД РАЗРЕШЁН**.
8. В `/admin` нажмите **Заблокировать** и отсканируйте → **БИЛЕТ ЗАБЛОКИРОВАН**.

**Проверка одновременного сканирования (гонка):** возьмите два телефона, откройте `/scan-in` на обоих и наведите на один QR одновременно. Вход зарегистрируется ровно один раз, второй телефон покажет «БИЛЕТ УЖЕ НАХОДИТСЯ НА ТЕРРИТОРИИ». Это гарантируется блокировкой строки `SELECT ... FOR UPDATE` внутри RPC-функции, а не логикой фронтенда.

Журнал всех попыток: Supabase → **Table Editor** → `scan_logs`.

## Шаг 10. Подключить свой домен (позже)

1. Vercel → ваш проект → **Settings** → **Domains** → **Add**.
2. Введите домен, например `tickets.ruhfest.kz`.
3. Vercel покажет DNS-запись. У регистратора домена добавьте:
   - для поддомена: `CNAME` `tickets` → `cname.vercel-dns.com`
   - для корневого домена: `A` `@` → IP, который укажет Vercel.
4. Подождите обновления DNS (обычно 5–60 минут). SSL-сертификат Vercel выпустит сам.

Важно: билеты, созданные до смены домена, содержат в QR старую ссылку. QR-код на публичной странице всегда генерируется от текущего адреса сайта, поэтому просто отправьте посетителю ссылку заново с новым доменом. Токен при этом не меняется.

## Как это защищено

- **Токен, а не номер.** Доступ к билету даёт только случайный токен на 32 байта (64 hex-символа), сгенерированный `gen_random_bytes` в базе. Номер `RUH-000001` секретом не является и подбор по нему невозможен.
- **Публичная страница ограничена.** Анонимный пользователь не имеет прав на таблицы вообще. Страница `/ticket/:token` работает через функцию `get_public_ticket`, которая возвращает только имя, номер и токен. Телефон, статус, журнал и список других билетов недоступны.
- **Смена статуса только на сервере.** Фронтенд не может выполнить `UPDATE status`. Вход и выход регистрируются RPC-функциями `register_ticket_entry` / `register_ticket_exit`, доступными только роли `authenticated`.
- **Атомарность.** Внутри функции строка билета блокируется `SELECT ... FOR UPDATE`, проверка и запись идут в одной транзакции. Два одновременных сканирования одного QR не могут оба зарегистрировать вход.
- **Нумерация в базе.** `RUH-000001` формируется PostgreSQL-sequence, а не подсчётом строк на клиенте.
- **service_role key во фронтенде отсутствует.** Используется только `anon key`, ограниченный политиками RLS.

## Коды ответа RPC

| Код | Экран | Что значит |
|---|---|---|
| `ENTRY_SUCCESS` | зелёный | вход разрешён, статус → `inside` |
| `EXIT_SUCCESS` | синий | выход зарегистрирован, статус → `outside` |
| `ALREADY_INSIDE` | красный | билет уже на территории, статус не меняется |
| `ALREADY_OUTSIDE` | красный | вход не был зарегистрирован, статус не меняется |
| `BLOCKED` | красный | билет заблокирован |
| `NOT_FOUND` | красный | токен не найден |
| `NOT_AUTHORIZED` | красный | сотрудник не авторизован |

Каждая попытка, успешная и неуспешная, записывается в `scan_logs`.
